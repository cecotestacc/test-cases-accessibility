Finding 1 — live-region-with-content is NOT in the JSON export

Definitive: rule never appears in any raw JSON export Cannot test via JSON

All 23 unique rule IDs found across all 3 scan runs were examined. Zero contain "live", "announce", or "dynamic". The complete list:

No live-region-with-content, live-region, or equivalent rule appears in any export.

Why: the rule's output is not written to the raw JSON export

The live-region-with-content issue type was observed in the portal HTML analysis of a real site (Puma-like) at the start of this project. However, QualiBooth's raw JSON export only captures a subset of its behavioral scan results. The live-region check may be:

  • Portal-UI computed only — calculated server-side and shown in the portal but not written to the export file.
  • Not implemented in the current scanner version — the rule may have been present in a different version of the scanner.
  • Requires runtime observation the export format doesn't capture — live-region monitoring requires observing MutationObserver events during real interaction; the export format may only record static scan results.
The rule cannot be verified via regression testing with the JSON export. Expected-results.html should not include a baseline for #toast-region live-region-with-content.
What #toast-region DOES show in the export

Across all 3 runs, #toast-region consistently appears with focus-obscured (Medium, AAA) on 2 pages with 6 occurrences. This is because the fixed-positioned toast element overlaps keyboard-focused content at the top-right of the viewport — a genuine accessibility issue, but not the intended live-region violation.

The current baseline for #toast-region is: 2/25 pages · 6 issues · Medium (AAA) focus-obscured. Accept this as the stable regression value.

Finding 2 — hover-focus fires on trending.html only (structural cause identified)

hover-focus behavioral check IS working — but placement-dependent Rule is functional

The hover-focus check fires correctly on trending.html. Three sub-rules were detected:

  • hover-focus-content/hover-only (High) — tooltip visible on :hover, not on :focus
  • hover-focus-content/not-dismissible (Medium) — no Escape key handler
  • hover-focus-content/not-hoverable (Medium) — tooltip disappears when pointer moves to it
This confirms the behavioral scanner CAN detect hover-focus violations. The rule IS implemented and working.
Root cause: tooltips inside <main> are not reached by the hover-focus scanner

trending.html (fires):

body > nav · div#promo-bar · div#cookie-banner · div.hero-section · div.page-hero
> div.content > [tooltips here]   ← tooltips are direct children of a body-level div

home.html (does not fire):

body > nav · div#promo-bar · div#cookie-banner
> MAIN > div.hero-section · div.page-hero · div.content
                              > [tooltips here]   ← tooltips inside <main>

The hover-focus behavioral scanner appears to simulate hover interactions only on elements that are accessible without entering a <main> landmark. On pages where the tooltip section is wrapped in <main> (home, shop-all, sale, new-arrivals, product pages), the scanner does not reach the tooltips. On trending.html (no <main> wrapper), the scanner can interact with them.

This is consistent with the page landmark structure: 17 of 25 pages are missing <main>. The hover-focus scanner behaves differently based on landmark presence.

Recommendations

1. Remove live-region-with-content from test targets

The rule is not in the JSON export. Update expected-results.html and test-coverage.html to remove #toast-region as a tested component for live-region violations. The current baseline (#toast-region → focus-obscured, 2 pages, Medium AAA) is the correct regression value.

The #toast-region page inventory can remain — it still tests the focus-not-obscured behavioral check and exercises the fixed-position element pattern.

2. Fix hover-focus to cover 2+ pages (make it a real shared component)

The hover-focus check works on trending.html because its tooltips are outside <main>. To get hover-focus rules to fire on 2+ pages (making them appear as shared components in the portal), either:

  • Option A: Move the tooltip section on one more page to be outside <main> — e.g., add tooltips to trending.html's sister page sale.html using the same non-<main> structure. But sale.html already has tooltips inside <main>.
  • Option B: On all 8 tooltip pages, move the tooltip section to BEFORE the <main> element — between the page-hero and <main>. This makes them consistently outside <main> and reachable by the hover-focus scanner.
  • Option C: Accept the current state — hover-focus fires on 1 page, which is below the 2-page threshold for shared component display.
Option B is the most thorough fix: move tooltip sections before <main> on all 8 tooltip pages. Expected result: hover-focus fires on 8 pages → appears as 3 shared components (hover-only High 8pg, not-dismissible Medium 8pg, not-hoverable Medium 8pg).
3. Update CLAUDE.md with live-region finding

Document in CLAUDE.md that live-region-with-content is not exported to the raw JSON and cannot be verified via the standard verification workflow. Add a note to the scan depth matrix marking it as "not in export format".
