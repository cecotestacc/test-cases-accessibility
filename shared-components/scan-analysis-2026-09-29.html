Bug details and root causes

Bug 1 — .newsletter-input: label rule never fires (placeholder accepted as label) Test design

Expected: label rule fires on 5 pages where .newsletter-input has no aria-label. Portal shows 5/25 pages, demonstrating "element present but no violation" on the 3 blog pages.

Actual: label rule fires on 0 pages. The placeholder="Your email address" attribute is accepted by axe-core as a sufficient accessible name — the label rule only fires when there is no accessible name whatsoever (no label, no aria-label, no aria-labelledby, no title, and no placeholder).

What is shown instead: The region rule fires on input for 5 pages, but the WRONG 5 pages: new-arrivals, trending, blog, blog-post-performance, blog-post-sustainability. This mixes violation pages (new-arrivals, trending) with non-violation pages (blog group) and misses home, shop-all, sale.

The "element present but no violation" test is completely non-functional. The label rule is not a reliable discriminator here. Fix: remove placeholder from all newsletter inputs, then add aria-label only on the pass pages. Without placeholder, the label rule will fire.

Fix: Change violation pages to <input type="email" class="newsletter-input"> (no placeholder). Add aria-label="Email address" only on blog, blog-post-performance, blog-post-sustainability. Verify label rule fires on exactly 5 pages.

Bug 2 — .tooltip-btn: aria-controls values differ per page, preventing grouping Test design

Expected: All 8 tooltip pages group under a single component (e.g. .tooltip-btn) with 8/25 pages.

Actual: Each page uses different aria-controls values. The selector generated by axe-core includes the attribute value (e.g. button[aria-controls="NONEXISTENT-ID-1"] vs button[aria-controls="nonexistent-id-1"] vs button[aria-controls="tooltip-info-1"]). This creates 9+ separate groups of 2–3 pages each instead of one group of 8.

Pages found: new-arrivals (nonexistent-id-*), product-running/training/shirts (NONEXISTENT-ID-*), trending (tooltip-info-*). Pages home, shop-all, sale used descriptive IDs like size-guide-panel which may actually resolve if a real element exists, or are grouped differently.

Fix: standardise all tooltip buttons to use the same nonexistent ID: aria-controls="tooltip-content" on every page. This produces one selector button[aria-controls="tooltip-content"] grouping all 8 pages together.
Bug 3 — #product-modal missing from product-accessories.html Implementation

Expected: 5/25 pages (product-running-shoes, product-training-shoes, product-shirts, product-jackets, product-accessories).

Actual: 4/25 pages — product-accessories.html does not contain #product-modal. The workflow agent for batch 2 (pages 6–10) did not add the modal to product-accessories despite the spec requiring it.

Fix: Add #product-modal and openModal()/closeModal() JS to product-accessories.html following the same pattern as product-running-shoes.html.
Bug 4 — h2.section-divider on blog.html uses selector "h2" not ".section-divider" Implementation

Expected: 3/25 pages under .section-divider (home, blog, faq).

Actual: home.html and faq.html produce selector .section-divider (2 pages ✓). blog.html's empty heading produces selector h2 (generic, no class) — placed in a different group.

Root cause: blog.html's empty heading was added without the class="section-divider" attribute, or the class was omitted by the edit.

Fix: Check blog.html's section-divider element and add class="section-divider" if missing.
Bug 5 — h3.section-title heading-order fires on only 14 of 20 expected pages Implementation

Expected: 20/25 pages trigger heading-order (h3 after h1 with no h2).

Actual: Only 14/25 pages trigger it. The portal shows 17 pages have the .section-title element, but heading-order only fires on 14. This means 6 pages have an h2 somewhere that "breaks" the skip (makes the h3 not a skip), and 3 pages are missing the element entirely.

The 6 pages where heading-order doesn't fire likely have an h2 added by the workflow agents (e.g. inside a card, a newsletter section, or the page-hero area), which satisfies the axe-core rule even though the h3.section-title still appears.

Fix: Audit pages 11–20 to confirm no h2 appears before h3.section-title. Remove any unintentional h2 elements on those pages. Also confirm pages 1–3 that appear to be missing the element actually have it.
Bug 6 — #toast-region live-region-with-content not detected Behavioral scan gap

Expected: 6 pages show "Live region created with content" violation on #toast-region.

Actual: Zero detections for any live-region rule. #toast-region only appears with a focus-not-obscured issue on 2 pages (the fixed-positioned toast covers keyboard-focused elements on small viewports).

Root cause: The "live region created with content" check requires the live region to be dynamically CREATED with content via JavaScript (i.e. the region doesn't exist at page load — it's injected). Static aria-live regions that have content in the initial HTML are not flagged by this rule in the current scanner version.

Fix: Change #toast-region to be injected via JS on page load with content already in the element — simulating a component that is dynamically added with pre-existing content. Use document.addEventListener('DOMContentLoaded', ...) to inject a region containing text. This matches the real-world failure pattern the rule targets.
Bug 7 — .ghost-cta and .modal-close: focus-visible not grouped by class selector Selector generation

Expected: .ghost-cta groups 18 pages under one component for focus-visible.

Actual: The scanner generates positional selectors for each ghost-cta link (html > body > main > div:nth-of-type(1) > a, etc.) because the link appears in different DOM positions on different pages. These scatter across many 1–3 page components.

Focus-visible IS detected on ghost-cta elements — the underlying rule fires — but the grouping key changes per page, preventing aggregation. The same applies to .modal-close.

This is a fundamental constraint: stable class selectors only group when the element consistently appears as the unique or primary element matching that class. If the same class selector resolves to one clear element per page, the class is used. If positional disambiguation is needed, the positional path is used instead. The fix is to ensure ghost-cta links have no other siblings matching the same axe selector criteria — or accept that focus-visible detection on links will scatter. Consider using an ID on a wrapper instead of relying on the class.

Fix option A: Wrap each ghost-cta in a unique-per-type container so the class selector is unambiguous. Fix option B: Accept this as a known scanner behaviour and remove .ghost-cta and .modal-close from the expected components list.

Bug 8 — 9 pages have QA panels causing noise components Implementation — agent error

The workflow agents added QA panels to 9 pages: account, blog-post-style, brands, faq, mens, orders, product-jackets, product-shirts, product-training-shoes, store-locator. These panels generate shared components in the portal: .qa-panel (9 pages, landmark issue), .qa-case-num (10 pages, AAA contrast), .qa-error-tag in multiple list positions (10 pages each, AAA contrast).

Fix: Remove QA panel HTML and CSS from all affected pages. The CLAUDE.md for this folder explicitly prohibits QA panels.

Severity label discrepancies

Expected Critical, got Medium/High — not a scanner bug

Three components showed lower severity than expected: meta[name="viewport"] (expected Critical, got Medium), .cookie-btn (expected Critical, got High), .flash-sale-chip (expected Critical, got High).

This is a mapping error in our expected results, not a scanner bug. QualiBooth uses its own 4-level scale (Critical/High/Medium/Low) which does not map 1:1 to axe-core's impact levels (critical/serious/moderate/minor):

  • meta-viewport — axe impact: critical → QualiBooth: Medium (AA level, non-urgent user impact)
  • color-contrast AA — axe impact: serious → QualiBooth: High
  • role-img-alt — axe impact: critical → QualiBooth: High
Fix: Update expected-results.html to use QualiBooth's actual severity labels, not axe-core impact labels. Record the correct mapping after this scan.

Unintended noise — not bugs, just observations

AAA colour contrast on almost every element

The scanner runs AAA colour contrast checks. Nearly all text elements fail AAA (enhanced contrast, 7:1 for normal text). This produces hundreds of components like .card:nth-child(N) > .price, .promo-line:nth-child(N), footer links, etc. These are all genuine AAA failures — our pages were designed for AA only. This is expected and not an error.

Missing landmark containment — pages without <main>

17 of 25 pages show "Document should have one main landmark" as a whole-page issue. The workflow agents structured some pages without a <main> element, causing all content to be outside landmarks. This produces the region rule firing on many selectors. The fix for this is adding <main> wrappers, but it requires auditing which pages are affected and is lower priority than the 8 bugs above.

Focus-not-obscured on cookie banner and footer links

The fixed-position #cookie-banner at the bottom of the viewport obscures keyboard-focused elements when the user tabs to elements near the bottom of the page. This was not planned but is a genuine accessibility issue — the cookie banner has no mechanism to dismiss or reposition. This is actually a good real-world finding but adds unplanned noise to the component list.
