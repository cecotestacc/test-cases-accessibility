Previously missing scenarios — now covered

Gap 1 — Low severity ADDED

Problem: Only Critical, High, and Moderate severity violations were present. The "Low" severity bucket in the portal would always appear empty, preventing verification that Low-severity components display correctly.

Solution: Added <h2 class="section-divider"></h2> (empty heading) to 3 pages: home.html, blog.html, faq.html. axe-core's empty-heading rule flags this as minor impact (= Low in QualiBooth).

Expected portal entry: h2.section-divider · 3/25 pages (12%) · 3 issues · 1 issue type (empty heading, Low)

What this verifies: Low severity badge renders correctly in the component list; issue count is accurate; share-of-run calculation works for small-count components.

Gap 2 — Minimum page count (1 and 2 pages) ADDED

Problem: The smallest component in the original set was 5 pages. Edge cases at 1 and 2 pages were untested — the portal might mis-calculate percentages, round incorrectly, or hide very small components.

Solution A (1 page): Added <section id="featured-promo" aria-checked="true"> to home.html only. aria-checked is not a permitted attribute on <section> → aria-allowed-attr violation (Critical).

Solution B (2 pages): Added <div class="flash-sale-chip" role="img"> (no accessible name) to sale.html and new-arrivals.html → role-img-alt violation (Critical).

#featured-promo · 1/25 pages (4%) · 1 issue · Critical
.flash-sale-chip · 2/25 pages (8%) · 2 issues · Critical

What this verifies: Portal handles single-digit page counts; percentage rounds correctly (4%, 8%); components aren't hidden or merged at low counts.

Gap 3 — Element present but no violation on some pages ADDED

Problem: Every original component either (a) existed and violated, or (b) didn't exist. There was no test for a component where the element exists on some pages with no violation — which is the common real-world case (e.g. a component fixed on some pages but broken on others).

Solution: Added <input type="email" class="newsletter-input"> to 8 pages in two configurations:

  • 5 pages — violation (home, shop-all, sale, new-arrivals, trending): input has no aria-label and no <label> → label violation (Critical).
  • 3 pages — no violation (blog, blog-post-performance, blog-post-sustainability): input has aria-label="Email address for newsletter" → passes axe-core.
Expected portal result: .newsletter-input · 5/25 pages · 5 issues — NOT 8/25 (element presence)
This is the key regression assertion: the portal groups by violation occurrence, not by element existence.

What this verifies: The shared components feature correctly counts only pages where a violation was found, not pages where the element merely exists. A mismatch here (showing 8 instead of 5) would indicate a fundamental bug in the grouping logic.

Key regression assertions

Primary: .newsletter-input shows 5/25, not 8/25 Must pass

The element exists on 8 pages but only violates on 5. The portal must show 5/25 pages (20%). Showing 8/25 (32%) would indicate the grouping counts element presence rather than violation occurrence — a fundamental feature defect.

Primary: #featured-promo shows exactly 1/25 Must pass

The element exists and violates on exactly 1 page (home.html). The portal must show 1/25 pages (4%). If the component is absent from the list or shows a different count, the minimum-threshold boundary condition is broken.

Secondary: h2.section-divider shows Low severity Must pass

The only Low-severity component. Must appear with the Low severity badge, 3/25 pages, and 3 issues. If it shows under a different severity or is absent, the Low-severity rendering path is broken.

All 16 components should appear in the Shared Components list Full behavioral scan

With a full behavioral scan, expect 16 entries. With axe-core only, expect 13 (the 3 behavioral-only issue types on nav.site-nav, .hero-section, and #product-modal may not appear). Document which mode was used for each regression run.
