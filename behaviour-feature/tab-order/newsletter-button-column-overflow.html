WCAG criteria
2.4.3 Focus Order — A
Elements under test
#newsletterOnlyEmail · #newsletterOnlyButton.klaviyo_form_trigger_footer · .catalogue-panel a
DOM tab order: email input → submit button → catalogue link (left-to-right, correct)
Expected result
  • PASS 0 tab-order violations — the DOM order matches the correct visual reading order for a two-column footer (left column first, then right column)
Why a scanner may false-positive
  • FALSE POSITIVE RISK #newsletterOnlyButton is 289px wide in a 285px column, centred → its right edge is 2px past the catalogue panel's left edge (e.g. button.right = 812.797 px, catalogue.left = 810.797 px). leadingSeparator requires a gap > 0 against the running maximum trailing edge, so those 2px erase the only column gutter in the footer — no column cut is made.
  • FALSE POSITIVE RISK Without a column cut, readingOrder falls through to its last resort: sort by top edge. The catalogue link sits at the top of its panel with no heading above it, so its top-y is smaller (higher on the page) than the email input, which is pushed down by the newsletter heading and intro paragraph. Top-edge sort places the catalogue link before the newsletter items — the opposite of DOM order — and the scanner reports "Focus jumps backwards through the visual reading order 1 time(s)" naming .klaviyo_form_trigger_footer.

Submit Button Overflow Erases Footer Column Gap

Scroll down to the footer. The newsletter "Sign me up!" button is 289 px wide inside a 285 px column. Its 2 px right-side overflow abuts the catalogue panel's left edge, preventing the geometry engine from detecting a column separator and triggering a false backwards-jump report.
