Case #04 tab-order FALSE POSITIVE
WCAG criteria
2.4.3 Focus Order — A
Elements under test
Footer links across four columns: SHOP · COMPANY · HELP · FOLLOW
Expected result
PASS No tab-order violation should be reported. The tab sequence follows DOM order, which matches the visual column-by-column layout exactly.
Why a scanner may false-positive
  • FALSE POSITIVE RISK A reading-order heuristic that models a 2-D grid left-to-right row-by-row (e.g. row 1: col1-item1, col2-item1, col3-item1, col4-item1 — then row 2…) will observe that the second link in column 2 (Contact) receives focus before the first link in column 3 (My Account) when both are in the same row. The scanner interprets this as an out-of-sequence jump and reports a likely reading-order mismatch.
  • This is incorrect: the DOM is authored column-by-column (<ul> per column, columns in source order SHOP → COMPANY → HELP → FOLLOW). The tab sequence follows DOM order precisely, and column-by-column navigation is the conventional and expected pattern for multi-column footer menus. No reordering is present.
  • The false positive is amplified when the page is dynamically mutating (e.g. lazy-loaded images, JS-driven content) during the tab walk — the scanner's snapshot of DOM order can diverge from what it actually walked, producing phantom mismatches.
Root cause of real issue (separate)
The only genuine tab-order problem in this pattern would be a tabindex value greater than 0 on a heading or other non-link element, which pulls it out of the natural sequence. That is a distinct, independently-flagged violation and not related to the footer column order.
