Case #15 focus-obscured FALSE POSITIVE
WCAG criteria
2.4.11 Focus Not Obscured (Minimum) — AA
Elements under test
Header navigation links (<a href="#home"> … <a href="#cart">) sitting behind the open div[role="dialog"][aria-modal="true"] backdrop (position:fixed; inset:0; z-index:200)
Expected result
  • PASS 0 focus-obscured violations — a scanner that recognises the obscurer is an open aria-modal="true" dialog not containing the focused element should emit one focus-obscured/behind-open-modal incomplete, not a per-control finding
Why a scanner may false-positive
  • FALSE POSITIVE RISK The traversal sweep programmatically moves focus to background elements outside the modal (via blurActive + direct element.focus()), bypassing the JS focus trap. Each stop is hit-tested as fully covered by the backdrop and reported as "The focused control is entirely covered by fixed html > body > div…". Real keyboard users cannot reach these elements while the modal is open — only the harness traversal can.
  • FALSE POSITIVE RISK The dialog is a hand-rolled div[role="dialog"][aria-modal="true"], not a top-layer <dialog>, so the browser does not mark background content inert. The sweep sees all background focusables in the DOM and includes them in its domOrder pass.
Root cause of real issue (separate)
Background content is not marked inert. Assistive technologies that do not honour aria-modal="true" for virtual-cursor containment can browse behind the overlay. This is a modal-lifecycle / keyboard-trap concern, not a focus-obscured finding.
